# Подготовка и выпуск

Публикация ещё не выполнялась. Workflow `release.yml` запускается только вручную (`workflow_dispatch`) из default branch и использует environment `npm`. Обычный push/PR запускает лишь проверки.

## Первоначальная настройка владельцем

1. Выберите доступное реальное npm-имя, замените временное имя в package.json, lockfiles, импортах примеров и документации. Добавьте реальные repository/homepage/bugs. Поле author добавляйте только с разрешёнными реальными данными.
2. Создайте публичный GitHub-репозиторий и отправьте код самостоятельно, когда будете готовы. Ни репозиторий, ни публикация автоматически в ходе разработки не создаются.
3. Настройте владельца/организацию npm и доступ к scope. Если настройки Trusted Publisher недоступны до первой версии, первоначальную публикацию выполняет владелец интерактивно с 2FA. Не добавляйте долгоживущий npm-токен в этот workflow.
4. В настройках npm-пакета добавьте GitHub Trusted Publisher: реальный owner/repository, имя файла `release.yml`, environment `npm`. Данные должны точно совпадать с workflow.
5. В GitHub создайте environment `npm`, ограничьте его default branch и включите нужные правила подтверждения релизов. Workflow имеет `id-token: write` для OIDC и `contents: write` для GitHub Release.
6. Проверьте public visibility репозитория/пакета для provenance. В workflow используется Node 24 и npm 11; минимальные требования npm Trusted Publishing — npm 11.5.1 и Node 22.14.0. [Официальная документация](https://docs.npmjs.com/trusted-publishers/).

## Обычный релиз

1. Выберите следующую версию SemVer: patch для исправлений, minor для совместимых возможностей, major для несовместимых изменений (в 0.x явно описывайте изменения API).
2. Выполните `npm version patch --no-git-tag-version` (или minor/major), обновите `CHANGELOG.md` с разделом `## x.y.z`. Выполните `npm run prepare:examples`, чтобы обновить пути и checksum локального tarball в примерах.
3. Выполните `npm run check`, `npm run test:consumer`, сборки примеров. Зафиксируйте изменения, проведите review и слейте в default branch самостоятельно.
4. В Actions → Release → Run workflow укажите подготовленную версию. Проверка запрещает временный scope, несовпадающую версию, отсутствие metadata/CHANGELOG и существующий tag. Разрешены стабильные версии major.minor.patch; prerelease-процесс отдельно не настроен.
5. После прохождения проверок workflow публикует npm-пакет через OIDC/provenance и создаёт GitHub Release с tag `vx.y.z`, привязанный к проверенному SHA.

Если npm publish завершился успешно, а создание GitHub Release — нет, **не перепубликовывайте** версию: создайте Release вручную для того же SHA. Если обнаружена ошибка в опубликованной версии, выпустите новую patch-версию; не переписывайте опубликованный tarball/tag.

GitHub Actions не запускался локально. Работоспособность OIDC зависит от реальной настройки владельца, которой пока нет. Локальные проверки не выполняют публикацию.
